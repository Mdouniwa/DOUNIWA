## 2026-07-13 PoC土台の初期実装

### 1. CLIフレームワークとして Typer / Click を採用する案

- **① 検討内容**: CLI実装に Typer（または Click）を使う。
- **② 却下理由**: PoC段階のサブコマンドは `run` と `models` の2つのみで、
  依存を増やす利点が薄い。依存最小化（httpx + python-dotenv のみ）を優先。
- **③ 代替**: 標準ライブラリ argparse。サブコマンドが増えて引数管理が
  煩雑になった時点で Typer への移行を再検討する（`app/cli/main.py` に集約済みなので移行コストは小さい）。

### 2. openai 公式 SDK を LLM クライアントに使う案

- **① 検討内容**: `openai` パッケージの `OpenAI(base_url=...)` で
  MLXサーバー/クラウドを叩く。
- **② 却下理由**: PoC で必要なのは `/chat/completions` への POST 1本のみ。
  SDK のバージョン追従・依存の重さに対して得るものが少ない。
  また stub フォールバック（未接続でも一本線を通す）を自前で制御しやすい方が良い。
- **③ 代替**: httpx による素の OpenAI互換 API 呼び出し（`app/llm/client.py`）。
  function calling / streaming が必要になった段階で SDK 採用を再検討。

### 3. タスク分類を最初からLLM（function calling）で行う案

- **① 検討内容**: 分類・ツール選択を最初からローカルLLMに任せる。
- **② 却下理由**: LLMサーバー未接続の環境では end-to-end 検証ができなくなる。
  「ダミーでも一本線が動く」という今日の完了条件と矛盾する。
  また分類品質のデバッグ対象が増え、土台の検証が遅れる。
- **③ 代替**: キーワードルール分類（`classifier.py`）。ただし
  `classify_task(str) -> Classification` のシグネチャを固定し、
  LLM分類への差し替えを P1 roadmap に明記。

### 4. モデル設定を YAML 外部ファイルにする案

- **① 検討内容**: `config/models.yaml` にモデル定義を書き、起動時にロードする。
- **② 却下理由**: モデル追加は開発者作業であり、コード（`models.py`）に
  dataclass で書く方が型チェック・IDE補完が効き、YAMLパーサ依存も不要。
  5モデル程度で外部化する必然性がない。
- **③ 代替**: `app/llm/models.py` 内のレジストリ + 環境変数による値の上書き。
  モデル数が2桁になる・非開発者が編集する必要が出た時点で外部化を再検討。

### 5. browser adapter を ToolAdapter と別系統のインターフェースにする案

- **① 検討内容**: browser/computer-use は対話的・状態保持型なので、
  単発実行の ToolAdapter とは別の専用インターフェースを設ける。
- **② 却下理由**: orchestrator から見える口が2系統になり、制御フローが分岐する。
  今日のスコープでは実装しないため、抽象化の正しさを検証する材料もない。
  過剰な抽象化の先取りになる。
- **③ 代替**: ToolAdapter（BrowserAdapter）+ 内部差し込み口 BrowserBackend の
  二段構え。状態保持は backend 実装側の責務とし、orchestrator への見え方は
  他ツールと統一。実装時に不足が判明したらこのログに追記して再設計する。

### 6. 最初から FastAPI サーバーとして実装する案

- **① 検討内容**: 将来のAPI化を見越して最初から FastAPI で組む。
- **② 却下理由**: 今日の入口は CLI のみ。「今いらないUIを作らない」方針に反する。
- **③ 代替**: orchestrator を CLI 非依存に設計（コンストラクタ注入・純粋な
  Python API）。将来 `app/api/` を被せるだけで API 化できる（roadmap P4）。
